## Context

当前 Portal 对话页在“消息流、输入区、结果卡片”三个区域存在层级冲突：消息在上方、结果卡片在下方重复展示，用户需要在多个位置来回确认结论与步骤。现有实现已具备多轮对话、引用展示和提单分流能力，因此本次重点是重组信息架构与视觉层级，不改动核心检索与提单业务逻辑。

约束：
- 保持现有 API 契约兼容（`/api/v1/ai/search`、handoff 相关接口）。
- 保持已有多轮对话状态机与错误处理分支。
- 遵循项目前端设计规范（浅色、品牌蓝系、足够留白）。

## Goals / Non-Goals

**Goals:**
- 将对话页统一为单一主流程：消息流 + 固定底部输入区，减少信息分裂。
- 将答案展示统一为“结论-步骤-验证-引用”，首屏即可执行。
- 提升消息可读性（气泡宽度、对齐、滚动体验、加载与错误反馈）。
- 保证移动端与桌面端均可稳定输入、发送、阅读。

**Non-Goals:**
- 不改检索排序算法与知识库索引内容。
- 不新增新的后端领域对象或数据库表。
- 不改提单流转策略（仅保留现有入口与文案优化）。

## Decisions

1. 单层主舞台布局（Conversation-first）
- 决策：聊天模式下使用全高 flex 容器，消息区 `flex:1` 可滚动，输入区固定在容器底部而非页面浮层。
- 原因：避免输入框悬浮覆盖内容、避免大面积空白与视觉断层。
- 备选：继续使用 `position: fixed` 输入框；被拒绝，因易与结果卡片/滚动产生冲突。

2. 回答信息采用结构化优先渲染
- 决策：优先渲染 `structured_answer.summary/steps/validation`；缺失时回退 `answer`。
- 原因：确保任意问题都能直观输出可执行步骤，而不是仅给摘要句。
- 备选：仅展示纯文本答案；被拒绝，执行性差。

3. 来源展示分层
- 决策：保留 Primary Source + More Sources + Citations，但将“可执行内容”置前，来源置后。
- 原因：先帮用户做事，再提供证据；兼顾效率与可追溯。
- 备选：来源置顶；被拒绝，阅读负担高。

4. UI 状态统一
- 决策：加载、错误、重试、继续追问使用同一消息流呈现，避免出现“提示在消息区、操作在卡片区”分裂。
- 原因：用户心智模型更一致。
- 备选：保留多处状态展示；被拒绝。

## Risks / Trade-offs

- [风险] 对话区与结果卡片同时保留可能仍有信息重复 → 缓解：将结果卡片收敛为结构化内容主展示，消息气泡仅保留当轮摘要。
- [风险] 输入区从 fixed 改为容器底部可能影响旧滚动行为 → 缓解：对消息区设置明确 `min-height:0 + overflow-y:auto` 并做移动端回归。
- [风险] 样式重构影响现有页面视觉一致性 → 缓解：限定样式作用域在聊天模式 class 下，避免外溢。
- [风险] 结构化字段为空时展示退化 → 缓解：前端回退到 `answer`，保证不空白。
